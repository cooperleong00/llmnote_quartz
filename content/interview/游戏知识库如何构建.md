# 游戏知识库如何构建

## 简短回答（30 秒版本）

我会采用**混合存储**：结构化数据库（SQL）存储装备属性等精确数据，向量数据库存储策略性知识用于语义检索。

**核心设计**：
- **数据层**：按实体类型分类（装备/英雄/机制），每个实体包含 metadata + 策略文档
- **向量化**：按语义单元切分（100-300 tokens），附加 metadata（版本号、可靠性）用于过滤
- **版本管理**：增量更新，保留历史版本，自动监听官方 API

这样既支持精确查询（"破败的攻击力"），又支持语义检索（"什么装备克制坦克"），且版本更新时只需增量更新。

## 深入解析

### 1. 核心问题分析

**问题本质**：构建一个能支持 LLM 准确回答游戏问题的知识库。

**关键挑战**：
- **双重查询需求**：既要精确查询（数值），又要语义检索（策略）
- **频繁更新**：游戏版本每 2 周更新一次
- **知识质量**：社区数据可靠性参差不齐
- **检索精度**：避免检索到过时或无关信息

### 2. 知识库分层设计

#### 2.1 为什么需要混合存储？

| 查询类型 | 示例 | 适合的存储 | 原因 |
|----------|------|------------|------|
| 精确查询 | "破败的攻击力是多少？" | SQL 数据库 | 结构化、快速、准确 |
| 语义检索 | "什么装备克制坦克？" | 向量数据库 | 理解语义、模糊匹配 |
| 关系推理 | "破败由哪些装备合成？" | 图数据库（可选） | 表达关系、路径查询 |

**架构**：

```
┌─────────────────────────────────────────┐
│  Layer 1: 结构化数据库（PostgreSQL）     │
│  - 装备属性表、英雄技能表、版本日志      │
│  - 用于精确查询、数值计算                │
└─────────────────────────────────────────┘
            ↓
┌─────────────────────────────────────────┐
│  Layer 2: 向量数据库（FAISS/Pinecone）  │
│  - 策略性知识（出装指南、对线技巧）      │
│  - 用于语义检索                          │
└─────────────────────────────────────────┘
            ↓
┌─────────────────────────────────────────┐
│  Layer 3: 图数据库（Neo4j，可选）       │
│  - 装备合成树、英雄克制关系              │
│  - 用于关系推理                          │
└─────────────────────────────────────────┘
```

- 结构化数据和策略知识分离，便于维护

### 5. 向量化策略（RAG 的核心）

#### 5.1 Chunk 切分策略

**错误做法**：
```markdown
# 破败王者之刃.md（整个文件作为一个 chunk）
破败是一件攻击装备，适合...（500 字）
```
→ 检索时噪音太多，无法精准定位

**正确做法**：按**语义单元**切分

```markdown
# 破败王者之刃.md

## 基础属性
[Chunk 1] 破败提供 40 攻击力、10% 吸血...

## 适用英雄
[Chunk 2] 破败适合攻速型 AD，如薇恩、卢锡安...

## 出装时机
[Chunk 3] 对线期领先时可以第一件出破败...

## 克制关系
[Chunk 4] 破败对高生命值英雄（如石头人）效果显著...
```

**Chunk 大小**：
- 太小（< 50 tokens）：缺少上下文
- 太大（> 500 tokens）：检索不精准
- **推荐**：100-300 tokens，保持语义完整

#### 5.2 Metadata 设计（关键！）

每个 chunk 附加元数据，用于**过滤 + 排序**：

```json
{
  "text": "破败适合攻速型 AD，如薇恩、卢锡安...",
  "metadata": {
    "entity_type": "item",
    "entity_id": "3153",
    "entity_name": "破败王者之刃",
    "section": "适用英雄",
    "version": "14.5",
    "reliability": "high",  // 数据来源可靠性
    "last_updated": "2024-03-01"
  },
  "embedding": [0.123, -0.456, ...]
}
```

**查询时的过滤**：
```python
# 用户问："现在版本破败适合谁？"
query_filter = {
    "entity_type": "item",
    "entity_name": "破败王者之刃",
    "version": "14.5",  # 只检索当前版本
    "section": "适用英雄"
}

results = vector_db.search(
    query_embedding,
    filters=query_filter,
    top_k=5
)
```

#### 5.3 Embedding 模型选择

| 模型 | 优势 | 劣势 | 适用场景 |
|------|------|------|----------|
| OpenAI `text-embedding-3-small` | 通用性好 | 对游戏术语理解一般 | 快速原型 |
| 领域微调的 Embedding | 理解游戏黑话 | 需要标注数据 | 生产环境 |
| BGE / M3E（中文） | 中文效果好 | 英文术语可能不准 | 中文为主 |

**推荐**：先用通用模型，后期用游戏对话数据微调。

### 6. 版本更新的自动化流程

```
┌─────────────────────────────────────────┐
│  1. 监听官方 API / Patch Notes           │
│     - 每周定时爬取                       │
│     - 检测 version 字段变化              │
└─────────────────────────────────────────┘
            ↓
┌─────────────────────────────────────────┐
│  2. Diff 检测                            │
│     - 对比新旧版本的 JSON                │
│     - 标记变更项（装备属性、英雄技能）   │
└─────────────────────────────────────────┘
            ↓
┌─────────────────────────────────────────┐
│  3. 更新结构化数据库                     │
│     - 插入新装备 / 更新属性              │
│     - 标记旧版本数据（不删除）           │
└─────────────────────────────────────────┘
            ↓
┌─────────────────────────────────────────┐
│  4. 触发策略知识更新                     │
│     - 自动生成"版本改动分析"文档         │
│     - 人工审核 + 补充                    │
└─────────────────────────────────────────┘
            ↓
┌─────────────────────────────────────────┐
│  5. 重新向量化                           │
│     - 只重新 embed 变更的 chunks         │
│     - 更新向量数据库                     │
└─────────────────────────────────────────┘
```

**关键设计**：
- **增量更新**：只更新变化的部分，不重建整个库
- **版本隔离**：保留历史版本数据，支持"上个版本怎么出装"的查询
- **人工审核**：自动化处理数值变化，策略性变化需要人工补充

### 7. 检索策略（RAG 的实现）

#### 7.1 混合检索

```python
def retrieve(user_query, game_state):
    # 1. 意图识别
    intent = classify_intent(user_query)

    # 2. 混合检索
    # 2a. 向量检索（语义相似）
    semantic_results = vector_db.search(
        query_embedding=embed(user_query),
        filters={"version": get_current_version()},
        top_k=5
    )

    # 2b. 关键词检索（精确匹配）
    keyword_results = sql_db.query(
        f"SELECT * FROM items WHERE name LIKE '%{extract_item_name(user_query)}%'"
    )

    # 3. 融合 + 重排序
    results = rerank(semantic_results + keyword_results, user_query)

    # 4. 上下文增强（加入游戏状态）
    context = f"""
    当前游戏状态：
    - 时间：{game_state['time']}
    - 经济：{game_state['gold']}
    - 对手英雄：{game_state['enemy_champions']}

    知识库检索结果：
    {results}
    """

    return context
```

#### 7.2 多跳检索（Multi-hop）

```
用户："薇恩出破败后下一件出什么？"
  ↓
第一跳：检索"薇恩出装顺序"
  → 得到"破败 → 飓风 → 智慧末刃"
  ↓
第二跳：检索"飓风 vs 智慧末刃的选择"
  → 得到"对面多坦克出智慧，多脆皮出飓风"
  ↓
结合游戏状态（对面 3 个坦克）→ 推荐智慧末刃
```

#### 7.3 负样本过滤

```python
# 避免检索到过时信息
filters = {
    "version": "14.5",
    "deprecated": False,  # 排除已删除的装备
    "reliability": {"$gte": 0.7}  # 只要可靠来源
}
```

### 8. 质量保障

#### 8.1 检索质量评估

```python
# 离线评估：准备测试集
test_cases = [
    {
        "query": "什么装备克制坦克？",
        "expected_items": ["破败", "智慧末刃", "破甲弓"],
        "game_state": {...}
    }
]

# 计算 Recall@K
for case in test_cases:
    retrieved = retrieve(case['query'], case['game_state'])
    recall = len(set(retrieved) & set(case['expected_items'])) / len(case['expected_items'])
```

#### 8.2 在线监控

- 记录用户反馈（"这个回答有用吗？"）
- 分析 bad case（用户标记"没用"的回答）
- 定期人工抽查（每周 100 条）

### 9. 成本优化

| 组件 | 成本来源 | 优化方案 |
|------|----------|----------|
| Embedding | API 调用费用 | 本地部署开源模型（BGE/M3E） |
| 向量数据库 | 存储 + 查询 | 用 FAISS（免费）而非 Pinecone |
| 数据更新 | 人工标注 | 优先自动化，只在关键节点人工介入 |
| LLM 推理 | 每次查询都调用 | 缓存高频问题的答案 |

## 面试官可能的追问

### 追问 1：为什么需要混合存储，不能只用向量数据库吗？

**为什么会问**：考察你对不同存储系统特点的理解。

**如何回答**：

"不能只用向量数据库，因为：

**向量数据库的局限**：
- 语义检索不适合精确查询（"破败的攻击力是多少？"）
- 数值计算困难（"破败 + 飓风的总攻击力"）
- 无法保证 100% 准确（embedding 有误差）

**混合存储的优势**：
- SQL：处理结构化数据、精确查询、数值计算
- Vector：处理语义检索、模糊匹配、策略推荐
- 各取所长，互补短板

**实际流程**：
1. 意图识别：判断是精确查询还是语义检索
2. 路由分发：精确查询 → SQL，语义检索 → Vector
3. 结果融合：如果需要，合并两者结果

**类比**：
- SQL 像字典：查'破败'的定义，快速准确
- Vector 像搜索引擎：查'克制坦克的装备'，理解语义"

### 追问 2：Chunk 切分有什么讲究？

**为什么会问**：考察你对 RAG 工程细节的理解。

**如何回答**：

"Chunk 切分直接影响检索精度，核心原则是**保持语义完整**。

**错误做法**：
- 按固定长度切分（如每 200 字）→ 可能切断语义
- 整个文档作为一个 chunk → 检索时噪音太多

**正确做法**：
- 按语义单元切分（如按章节、按问题）
- 每个 chunk 回答一个明确的问题

**Chunk 大小**：
- 太小（< 50 tokens）：缺少上下文，LLM 无法理解
- 太大（> 500 tokens）：检索不精准，包含无关信息
- **推荐**：100-300 tokens

**示例**：
```markdown
# 破败王者之刃.md

## 适用英雄
[Chunk 1] 破败适合攻速型 AD，如薇恩、卢锡安，
因为被动触发频率高，能最大化百分比伤害。

## 出装时机
[Chunk 2] 对线期领先时可以第一件出破败，
能进一步扩大优势；劣势时建议先出防御装。
```

**关键**：每个 chunk 都能独立回答一个问题"

### 追问 3：Metadata 为什么重要？

**为什么会问**：考察你对 RAG 精度优化的理解。

**如何回答**：

"Metadata 是提高检索精度的关键，它让我们能**过滤而非仅依赖相似度**。

**没有 Metadata 的问题**：
```python
# 用户问："现在版本破败适合谁？"
# 纯向量检索可能返回：
- 14.3 版本的破败攻略（过时）
- 其他装备的适用英雄（无关）
- 破败的合成路径（不是用户想要的）
```

**有 Metadata 的优势**：
```python
filters = {
    "entity_name": "破败王者之刃",  # 只检索破败相关
    "section": "适用英雄",          # 只要这个章节
    "version": "14.5",              # 只要当前版本
    "reliability": {"$gte": 0.7}    # 只要可靠来源
}
```

**Metadata 设计**：
- entity_type / entity_name：定位实体
- section：定位章节
- version：版本过滤
- reliability：来源可靠性
- last_updated：新鲜度

**效果**：
- 检索精度从 60% 提升到 90%+
- 避免过时信息
- 减少无关结果"

### 追问 4：版本更新时如何保证不中断服务？

**为什么会问**：考察你对生产系统可用性的理解。

**如何回答**：

"我会采用**蓝绿部署 + 增量更新**策略：

**1. 蓝绿部署**：
```
┌─────────────┐      ┌─────────────┐
│  蓝环境      │      │  绿环境      │
│  (当前版本)  │ ←─── │  (新版本)    │
│  14.4        │      │  14.5        │
└─────────────┘      └─────────────┘
       ↑                    ↑
       │                    │
   用户流量              测试流量
```

**流程**：
1. 在绿环境更新知识库（14.5 版本）
2. 内部测试验证（检索准确性、响应时间）
3. 灰度发布（10% 流量 → 绿环境）
4. 监控指标（错误率、延迟）
5. 全量切换（100% 流量 → 绿环境）
6. 保留蓝环境 24 小时（快速回滚）

**2. 增量更新**：
- 只更新变更的装备/英雄
- 只重新向量化变更的 chunks
- 避免全量重建（节省时间和成本）

**3. 版本共存**：
- 同时保留 14.4 和 14.5 的数据
- 用户可以查询历史版本（'上个版本怎么出装'）
- 数据库用 version 字段区分

**4. 监控告警**：
- 检索延迟 > 2s → 告警
- 错误率 > 5% → 自动回滚
- 用户反馈负面 > 20% → 人工介入"

### 追问 5：如何评估知识库的质量？

**为什么会问**：考察你对系统评估的全面性。

**如何回答**：

"我会从三个维度评估：

**1. 覆盖度**（Completeness）：
- 装备覆盖率：当前版本所有装备都有文档
- 英雄覆盖率：所有英雄都有对线/团战指南
- 场景覆盖率：常见问题（出装/对线/团战）都能回答

**2. 准确性**（Accuracy）：
- 数值准确性：装备属性与官方 API 一致（自动验证）
- 策略准确性：高段位玩家审核（人工抽查）
- 检索准确性：Recall@5 > 90%（离线评估）

**3. 新鲜度**（Freshness）：
- 版本同步：新版本发布后 24 小时内更新
- 元数据更新：每个 chunk 有 last_updated 字段
- 过时检测：自动标记 > 2 个版本的旧数据

**评估方法**：

**离线评估**：
```python
test_cases = [
    {"query": "什么装备克制坦克？", "expected": ["破败", "智慧末刃"]},
    {"query": "薇恩对线德莱文怎么打？", "expected": ["猥琐发育", "等打野"]}
]

for case in test_cases:
    retrieved = retrieve(case['query'])
    recall = compute_recall(retrieved, case['expected'])
```

**在线监控**：
- 用户反馈：每次对话后评分（1-5 星）
- Bad case 分析：用户标记'没用'的回答
- A/B 测试：新旧知识库对比

**持续优化**：
- 每周分析 top 10 bad cases
- 补充缺失的知识
- 优化检索策略（调整 top_k、相似度阈值）"

## 记忆要点

**核心框架**（必须记住）：
```
混合存储 = SQL（精确） + Vector（语义） + Graph（关系，可选）
```

**三个关键设计**：
1. **按语义单元切分**：100-300 tokens，保持完整性
2. **Metadata 驱动过滤**：版本号、实体类型、可靠性
3. **增量更新**：只更新变化部分，不重建整个库

**向量化三要素**：
- Chunk 切分：按语义单元
- Metadata 设计：版本、实体、章节、可靠性
- Embedding 模型：通用模型 → 领域微调

**版本管理**：
- 蓝绿部署：保证不中断服务
- 版本隔离：保留历史数据
- 自动监听：官方 API → Diff → 更新

**对比记忆**：
- vs 纯向量库：混合存储更准确
- vs 固定切分：语义切分更精准
- vs 全量重建：增量更新更高效
