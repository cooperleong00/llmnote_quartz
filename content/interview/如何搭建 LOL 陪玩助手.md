# 如何搭建 LOL 陪玩助手

## 简短回答（30 秒版本）

我会采用**混合架构**：规则引擎处理实时确定性任务（龙团倒计时、装备克制），LLM + RAG 处理开放性咨询（策略建议、对线技巧）。

**核心设计**：
- **数据层**：结构化数据库（装备属性）+ 向量数据库（策略知识）
- **推理层**：意图识别 → 路由分发 → 规则引擎 / LLM
- **优化**：用 RAG 解决版本更新问题，用 DPO 优化语气

这样既保证实时性，又保证灵活性，且版本更新时只需更新知识库而非重训练模型。

## 深入解析

### 1. 核心问题分析

**问题本质**：设计一个能理解游戏状态、提供实时建议、自然交互的 AI 助手。

**关键挑战**：
- **实时性**：游戏内决策窗口短（龙团提醒需要提前 30-60 秒）
- **准确性**：装备数据、英雄技能等事实性知识不能出错
- **可维护性**：游戏版本频繁更新（每 2 周一次）
- **自然度**：避免机器人式的生硬回复

### 2. 整体架构设计

```
用户输入（文本）
    ↓
┌─────────────────────────────────────────┐
│  游戏状态监听模块                        │
│  - 当前时间、小龙刷新、装备、经济        │
└─────────────────────────────────────────┘
    ↓
┌─────────────────────────────────────────┐
│  意图识别 + 路由层                       │
│  - 实时提醒 → 规则引擎                   │
│  - 策略咨询 → LLM + RAG                  │
└─────────────────────────────────────────┘
    ↓                           ↓
┌──────────────┐      ┌──────────────────┐
│  规则引擎     │      │  LLM 推理层       │
│  - 龙团倒计时 │      │  - Base: 7B 模型  │
│  - 装备克制   │      │  - SFT: 游戏知识  │
│  - 经济警告   │      │  - DPO: 语气优化  │
└──────────────┘      └──────────────────┘
                            ↓
                  ┌──────────────────────┐
                  │  知识库（RAG）        │
                  │  - 装备数据库         │
                  │  - 英雄技能库         │
                  │  - 版本更新日志       │
                  └──────────────────────┘
```

**架构分层**：

| 层级 | 组件 | 职责 | 技术选型 |
|------|------|------|----------|
| 输入层 | 游戏状态监听 | 读取游戏 API/内存 | 游戏官方 API |
| 路由层 | 意图识别 | 判断问题类型 | 轻量分类模型 |
| 执行层 | 规则引擎 | 确定性逻辑 | Python 规则系统 |
| 执行层 | LLM + RAG | 开放性问答 | 7B 模型 + 向量检索 |
| 数据层 | 知识库 | 游戏知识存储 | PostgreSQL + FAISS |

### 3. 数据选择与准备

#### 3.1 数据来源

**游戏知识数据**（用于 RAG）：
- **结构化数据**：装备属性、英雄技能、地图机制
  - 来源：官方 API（Riot Games API）
  - 存储：PostgreSQL（精确查询）
- **策略性知识**：出装顺序、对线技巧、团战定位
  - 来源：高分段对局解说、社区攻略（OP.GG、Reddit）
  - 存储：向量数据库（语义检索）

**对话数据**（用于 SFT）：
- 真实陪玩对话记录（如果有）
- 合成数据：用 LLM 生成"玩家提问 + 助手回答"对
  ```
  示例：
  Q: "现在出什么装备好？"
  A: "你现在领先 800 金币，可以考虑第一件出破败，
      对面上单是石头人，破败的百分比伤害很有效。"
  ```

**偏好数据**（用于 DPO）：
- 标注"生硬 vs 自然"的回复对比
  ```
  Rejected: "建议您购买破败王者之刃装备。"
  Chosen: "可以试试破败，对面坦克多，百分比伤害很香。"
  ```

#### 3.2 数据组织

知识库采用**混合存储**：

```
knowledge_base/
├── structured/          # 结构化数据（SQL）
│   ├── items.json      # 装备属性
│   ├── champions.json  # 英雄技能
│   └── version.json    # 版本信息
│
└── semantic/           # 语义知识（向量化）
    ├── build_guides/   # 出装指南
    ├── matchups/       # 对线克制
    └── tactics/        # 战术决策
```

### 4. 关键技术方案

#### 4.1 RAG 架构（解决版本更新问题）

**为什么用 RAG 而非训练到模型里？**
- 装备属性是**事实性知识**，频繁变化（每 2 周）
- 重训练成本高（数据、算力、时间）
- 模型容易产生幻觉（记错数值）

**RAG 流程**：
```python
def answer_query(user_query, game_state):
    # 1. 意图识别
    intent = classify(user_query)  # "装备推荐" / "战术决策"

    # 2. 混合检索
    # 2a. 向量检索（语义相似）
    semantic_results = vector_db.search(
        embed(user_query),
        filters={"version": "14.5"},  # 只检索当前版本
        top_k=5
    )

    # 2b. 精确查询（数值数据）
    if "破败" in user_query:
        item_data = sql_db.query(
            "SELECT * FROM items WHERE name='破败'"
        )

    # 3. 构造 prompt
    context = f"""
    当前游戏状态：{game_state}
    装备数据：{item_data}
    策略建议：{semantic_results}
    """

    # 4. LLM 生成
    return llm.generate(context + user_query)
```

**版本更新时的操作**：
1. 监听官方 API，检测版本变化
2. 更新结构化数据库（装备属性）
3. 重新向量化变更的策略文档
4. **模型本身不变**，推理时自动使用最新数据

#### 4.2 语气优化（解决生硬问题）

**短期方案**（无需重训练）：

1. **Prompt Engineering**：
   ```
   你是友好的 LOL 陪玩助手，说话风格：
   - 用"咱们"而非"你"
   - 用游戏黑话（"对面 AD 没闪"）
   - 鼓励性语气（"稳住，能赢！"）

   错误示例："建议您购买破败王者之刃。"
   正确示例："可以出破败，对面坦克多很有用。"
   ```

2. **后处理规则**：
   - 替换生硬词汇："建议" → "可以试试"
   - 添加语气词："哦"、"呢"、"吧"

**长期方案**（需要数据）：

使用 [[DPO]]（Direct Preference Optimization）微调：
- 收集 1000+ 对"生硬 vs 自然"的回复对比
- 在现有模型基础上做偏好对齐
- **优势**：不需要重新训练整个模型，只需 1-2 天微调

#### 4.3 实时提醒（龙团场景）

**规则引擎**（确定性逻辑）：

```python
# 触发条件
if game_time in [5:00, 10:00, 15:00]:  # 小龙刷新时间
    if dragon_alive and time_to_spawn < 60:
        if player_in_lane and distance_to_dragon > 3000:
            # 触发提醒
            context = {
                "time_left": time_to_spawn,
                "gold_diff": our_gold - enemy_gold,
                "player_position": "上路对线",
                "player_intent": last_user_message  # "我想推塔"
            }
            reminder = llm.generate_reminder(context)
```

**LLM 增强**（上下文感知）：

规则引擎只决定"是否提醒"，LLM 决定"如何提醒"：

```
输入：
- 小龙刷新倒计时 30 秒
- 我方经济落后 2000
- 对面打野有惩戒
- 玩家刚说"我想继续推塔"

LLM 输出：
"小龙快刷了，但咱们经济落后，对面打野有惩戒，这波不太好接。
你继续推上路塔，让队友试探一下，能抢就抢，抢不到也别送。"
```

### 5. 设计权衡

#### 5.1 为什么用混合架构而非纯 LLM？

| 方案 | 优势 | 劣势 | 适用场景 |
|------|------|------|----------|
| 纯 LLM | 灵活、自然 | 慢、不稳定、可能出错 | 开放性咨询 |
| 纯规则 | 快、准确 | 僵硬、无法处理复杂问题 | 实时提醒 |
| **混合** | **各取所长** | 架构复杂 | **生产环境** |

**决策依据**：
- 实时性要求高 → 规则引擎
- 需要理解上下文 → LLM
- 事实性知识 → RAG

#### 5.2 为什么选 7B 模型而非更大？

- **延迟要求**：游戏内交互需要 < 2 秒响应
- **成本考虑**：7B 可以本地部署，降低 API 成本
- **效果足够**：游戏助手不需要复杂推理，7B + RAG 足够

#### 5.3 替代方案

**方案 A**：完全基于规则系统
- 优势：快、稳定
- 劣势：无法处理"我现在该干嘛？"这类开放问题

**方案 B**：纯 LLM + 微调
- 优势：最自然
- 劣势：版本更新需要重训练，成本高

**方案 C**（推荐）：混合架构 + RAG + DPO
- 平衡了实时性、灵活性、可维护性

### 6. 边界与局限

**什么情况下这个方案不适用？**

1. **极低延迟要求**（< 100ms）：
   - LLM 推理至少需要 500ms-2s
   - 解决：纯规则系统 + 预计算

2. **离线环境**：
   - 需要本地部署 7B 模型 + 向量数据库
   - 解决：边缘设备可能性能不足

3. **多模态输入**（小地图视觉）：
   - 当前方案只处理文本
   - 解决：需要加入 CV 模型识别游戏画面

**可能的问题**：
- **RAG 检索不准**：需要持续优化 embedding 和 metadata 过滤
- **LLM 幻觉**：需要在 prompt 中强调"不确定时说不知道"
- **规则维护成本**：游戏机制变化时需要更新规则

## 面试官可能的追问

### 追问 1：如果用户发现助手语气太生硬，怎么解决？

**为什么会问**：考察你对 post-training 技术的理解，以及短期/长期方案的权衡。

**如何回答**：

"我会分短期和长期两个方案：

**短期**（1-2 天内上线）：
- Prompt engineering：在 system prompt 中加入语气指导和 few-shot 示例
- 后处理规则：替换生硬词汇（'建议' → '可以试试'）

**长期**（1-2 周）：
- 收集偏好数据：标注 1000+ 对'生硬 vs 自然'的回复
- 用 DPO 微调：在现有模型基础上做偏好对齐
- 优势：不需要重新训练整个模型，成本低

**为什么选 DPO 而非 RLHF**：
- DPO 更简单（单阶段训练，不需要 reward model）
- 更稳定（避免 RL 训练的不稳定性）
- 更快（1-2 天即可完成微调）"

### 追问 2：版本更新后装备变了，模型需要重训练吗？

**为什么会问**：考察你对 RAG 的理解，以及知识更新策略。

**如何回答**：

"**不需要重训练**，这正是我用 RAG 的原因。

**核心思路**：知识与模型解耦
- 装备属性存在知识库（数据库 + 向量库）
- 模型只负责理解问题和生成回答
- 推理时动态检索最新数据

**版本更新流程**：
1. 监听官方 API，检测版本变化
2. 更新结构化数据库（装备属性、数值）
3. 重新向量化变更的策略文档（如'破败削弱后的出装'）
4. 模型本身不变，自动使用新数据

**为什么不训练到模型里**：
- 事实性知识容易产生幻觉
- 重训练成本高（数据、算力、时间）
- 版本更新频繁（每 2 周），不可持续

**额外优化**：
- 知识库加入版本号字段，支持'上个版本怎么出装'的查询
- 定期爬取官方 API 自动更新"

### 追问 3：如何保证 RAG 检索的准确性？

**为什么会问**：考察你对 RAG 工程实践的深度理解。

**如何回答**：

"我会从三个层面保证准确性：

**1. Metadata 过滤**（最重要）：
```python
filters = {
    'version': '14.5',        # 只检索当前版本
    'entity_type': 'item',    # 只检索装备相关
    'reliability': {'$gte': 0.7}  # 只要可靠来源
}
```

**2. 混合检索**：
- 向量检索：处理语义相似（'什么装备克制坦克'）
- 关键词检索：处理精确匹配（'破败的攻击力'）
- 融合排序：结合两者结果

**3. 质量评估**：
- 离线评估：准备测试集，计算 Recall@K
- 在线监控：记录用户反馈（'这个回答有用吗？'）
- 人工审核：高频错误案例人工修正

**常见问题**：
- 检索到过时信息 → 用 version 字段过滤
- 检索结果太多噪音 → 调整 top_k 和相似度阈值
- 专业术语理解不准 → 用游戏对话数据微调 embedding 模型"

### 追问 4：如果是小龙团场景，怎么做提醒规划？

**为什么会问**：考察你对实时系统和上下文感知的理解。

**如何回答**：

"我会用**规则引擎 + LLM**的组合：

**规则引擎**（判断'何时提醒'）：
```python
if time_to_dragon < 60:  # 小龙刷新倒计时
    if player_distance > 3000:  # 玩家在远处
        if not already_reminded:  # 避免重复提醒
            trigger_reminder()
```

**LLM**（决定'如何提醒'）：
- 输入游戏状态：经济差距、对面打野位置、玩家当前意图
- 生成上下文感知的建议：
  ```
  优势局："小龙快刷了，咱们经济领先，可以提前占视野"
  劣势局："小龙快刷了，但咱们落后，你继续推塔，让队友试探"
  ```

**关键设计**：
- 规则保证实时性（< 100ms 判断）
- LLM 保证灵活性（理解局势）
- 避免打断玩家（正在团战时不提醒）

**进阶**：
- 多模态输入：用 CV 识别小地图，判断敌方位置
- 预测性提醒：'对面打野可能去偷龙'（基于行为模式）"

### 追问 5：如何评估这个系统的效果？

**为什么会问**：考察你对产品指标和 A/B 测试的理解。

**如何回答**：

"我会设计多层次的评估指标：

**1. 技术指标**：
- 响应延迟：P50 < 1s，P99 < 3s
- RAG 准确率：Recall@5 > 90%
- 模型幻觉率：< 5%（人工抽查）

**2. 用户体验指标**：
- 对话轮次：平均 3-5 轮解决问题
- 用户满意度：每次对话后评分（1-5 星）
- 重复使用率：7 日留存 > 40%

**3. 业务指标**：
- 用户胜率提升：使用助手 vs 不使用
- 付费转化率：免费 → 付费会员

**A/B 测试**：
- 对照组：纯规则系统
- 实验组：混合架构 + RAG
- 观察：用户满意度、留存率差异

**持续优化**：
- 收集 bad case（用户反馈'这个回答没用'）
- 分析失败原因（检索不准 / 生成不当）
- 迭代优化（更新知识库 / 调整 prompt）"

## 记忆要点

**核心框架**（必须记住）：
```
混合架构 = 规则引擎（实时） + LLM（灵活） + RAG（知识）
```

**三个关键设计**：
1. **RAG 解决版本更新**：知识与模型解耦，只更新数据库
2. **DPO 优化语气**：偏好对齐，不需要重训练
3. **规则 + LLM 做提醒**：规则判断"何时"，LLM 决定"如何"

**数据分层**：
- 结构化（SQL）：装备属性、数值
- 语义化（Vector）：策略知识、技巧
- 对话数据（SFT）：自然交互
- 偏好数据（DPO）：语气优化

**对比记忆**：
- vs 纯 LLM：混合架构更快、更准
- vs 纯规则：混合架构更灵活
- vs 训练到模型：RAG 更易维护
