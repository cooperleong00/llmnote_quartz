# Agent Harness for Large Language Model Agents (2026)

这篇综述把智能体 harness（agent harness）定义为围绕大语言模型智能体的运行时治理基础设施。它的核心贡献是形式化六组件框架 $\mathcal{H}=(E,T,C,S,L,V)$，并用历史脉络、完整性矩阵和技术挑战分析说明：长程智能体的可靠性由模型能力和 harness 设计共同决定。

这篇论文适合作为独立综述笔记阅读，因为它的价值集中在综述级综合：正式定义、历史谱系、系统分类、矩阵化比较、挑战地图和研究路线。它与 [[Agent Harness Engineering (2026)|Agent Harness Engineering]] 关注同一个基础设施转向；这篇论文用 $\mathcal{H}=(E,T,C,S,L,V)$ 描述运行时治理面，后者用 ETCLOVG 七层分类强调更宽的工程层次，包括可观测性和治理层。

## 一句话定位

LLM 智能体 harness 是把模型能力转化为可执行、可恢复、可审计行为的运行时外壳。它管理执行循环、工具、上下文、状态、策略钩子和评估接口，让智能体在真实环境中完成多步任务时有明确的边界、反馈和证据。

> [!intuition] 为什么 harness 会成为研究对象
> 单次模型调用只需要输入和输出；长程智能体需要持续观察环境、选择工具、处理失败、记住中间状态、接受权限约束，并留下可复现的轨迹。Harness 研究的对象正是这些运行时治理功能。

论文用多组经验现象支撑这一判断：固定模型时，harness 层改动可以在代码基准、终端任务和数学推理上带来显著增益；[[SWE-Bench]]、HAL、AgencyBench 等评估工作也显示，基准分数经常反映的是模型、harness 和环境三者的组合表现。

## 六组件定义

> [!definition] 智能体 Harness
> 智能体 harness 是一个软件系统 $\mathcal{H}=(E,T,C,S,L,V)$，实现六类运行时治理功能：执行循环、工具注册表、上下文管理器、状态存储、生命周期钩子和评估接口。最小 harness 至少需要 $E$ 和 $T$，完整生产级 harness 需要六个组件都具备可靠实现。

| 符号 | 中文名 | 负责的问题 | 典型失效 |
|---|---|---|---|
| $E$ | 执行循环 | 观察、推理、行动、终止和错误恢复如何推进 | 无限循环、过早停止、失败后无法恢复 |
| $T$ | 工具注册表 | 工具有哪些、怎样校验参数、怎样路由调用 | 工具误用、过宽权限、工具结果污染上下文 |
| $C$ | 上下文管理器 | 每一步模型能看到什么信息 | 上下文爆炸、关键状态丢失、注入内容长期滞留 |
| $S$ | 状态存储 | 哪些任务状态跨轮次或跨会话持久化 | 中断后状态丢失、记忆污染、并发写入冲突 |
| $L$ | 生命周期钩子 | 在调用前后执行鉴权、审计、策略和安全检查 | 越权行动、缺少审批、侧效应不可追踪 |
| $V$ | 评估接口 | 如何记录轨迹、状态和成功信号，供评估系统使用 | 只能看最终结果，无法归因失败或比较 harness |

六个组件分成三组治理面。$E$ 和 $T$ 管模型如何接触外部世界；$C$ 和 $S$ 管模型可见的信息与可持久化的状态；$L$ 和 $V$ 管策略、审计、可观测性和评估证据。

### 为什么 $V$ 和 $L$ 要分开

生命周期钩子 $L$ 负责运行时控制，例如鉴权、拦截、日志和策略执行。评估接口 $V$ 负责把行为轨迹整理成可被基准、观测平台或事后分析消费的标准结构。

一个系统可以记录“某个工具被调用了”，这仍然只是 $L$ 层日志；当它能记录动作类型、参数结构、上下文快照、工具结果、token 成本、目标进度和成功信号，并让外部评估管线直接消费时，才具备 $V$ 组件。论文认为 $V$ 是最常欠缺的组件之一，这解释了为什么很多智能体系统能运行，却难以被公平评估。

### 执行循环的形式化视角

论文进一步把 $E$ 组件写成标记迁移系统（labeled transition system, LTS）：

$$
Q=\{\text{idle},\text{observing},\text{invoking-model},\text{dispatching-tool},\text{awaiting-tool-result},\text{committing-state},\text{terminated}\}
$$

$$
\delta: Q \times \Sigma \rightarrow Q
$$

这里 $Q$ 是 harness 的运行状态集合，$\Sigma$ 是可观察事件集合，$\delta$ 是状态迁移函数。这个形式化让三个性质变得可讨论：安全性要求系统不会进入无法终止或越权的状态；活性要求非终止状态仍能到达终止状态；确定性要求环境非确定性被隔离在工具调用边界，方便复现和调试。

这个视角能区分几类系统。ReAct 风格循环只有简化的“活动/完成”状态，错误恢复和状态提交语义较弱；AutoGPT 有更完整的循环结构，但早期实现缺少生产级状态保证；[[LangGraph]] 用图拓扑表达执行流，能把一部分活性约束编码进图结构。

## 历史演化：三个谱系汇合

论文把智能体 harness 的形成解释为三条技术谱系的汇合。

| 谱系 | 提供的思想 | 带来的局限 |
|---|---|---|
| 软件测试 harness | 用外部治理外壳控制输入、输出、隔离、setup/teardown 和结果记录 | 面向确定性、单次、边界清晰的程序执行 |
| 强化学习环境 | 用标准接口定义 observation、action、reward、reset，便于评估和复现 | 假设动作空间较固定、任务较短、奖励可标量化 |
| 早期 LLM 智能体框架 | ReAct、AutoGPT、Voyager、MemGPT、Reflexion 等暴露了真实失败模式 | 许多方案把治理逻辑嵌在应用代码里，缺少可替换的基础设施边界 |

这三条线分别贡献了治理外壳、接口标准和失败模式目录。LLM 智能体 harness 把它们组合成面向开放环境、自然语言任务、多工具行动和长时间运行的运行时治理系统。

论文还把 2022-2026 的工程关注点划成三个阶段。提示词工程关注一次调用给模型什么文本；[[Context Engineering|上下文工程]]关注每一步应组织什么信息；harness 工程把关注范围扩展到完整的执行、工具、状态、策略和评估闭环。[[Context Compression|上下文压缩]]、[[RAG|检索增强生成]]、技能注入和工具裁剪都可以放进这一更大的 harness 视角中理解。

## 完整性矩阵如何读

论文用 23 个系统构造完整性矩阵，逐项标注 $E,T,C,S,L,V$ 的实现程度，并额外记录安全模型与多智能体支持。矩阵的用途是帮助读者判断一个系统在栈中的位置：它是可直接部署的运行时、构建智能体的开发框架、某个治理组件模块，还是评估基础设施。

| 系统类别 | 典型系统 | 矩阵特征 | 设计含义 |
|---|---|---|---|
| 全栈 harness | Claude Code, OpenClaw/PRISM, Hermes, AIOS, OpenHands | $E,T,C,S,L$ 较完整，$V$ 常有差异 | 面向真实部署，harness 本身承担大部分治理职责 |
| 多智能体 harness | MetaGPT, AutoGen, ChatDev, CAMEL, DeerFlow, DeepAgents | $E,T$ 较强，$C,S,L,V$ 多为部分实现 | 关注多智能体协作，状态一致性和身份治理成为核心问题 |
| 通用开发框架 | LangChain, LangGraph, LlamaIndex | 提供构建原语，运行时治理常交给使用者 | 适合搭建系统，生产可靠性取决于额外 harness 设计 |
| 能力模块 | MemGPT, Voyager, Reflexion, Generative Agents | 强在 $C$ 或 $S$，弱在全局编排 | 是 harness 的可复用组件，单独使用时覆盖面有限 |
| 评估基础设施 | HAL, AgentBench, OSWorld, BrowserGym | $V$ 和环境控制较强 | 评估系统本身也是 harness 工程成果 |

> [!intuition] 矩阵真正揭示的东西
> 系统成熟度沿着多条设计轴变化。不同系统会为了不同目标省略不同组件：框架把治理留给开发者，模块专注某个组件，评估基础设施把可复现和轨迹记录放在优先级最高的位置。

完整性矩阵还暴露了一个模块化缺口：$T$ 组件已经有 [[Model Context Protocol|MCP]] 这类标准化努力，$C$ 组件也有 MemGPT、Zep、上下文压缩等成熟方向；$S$、$L$、$V$ 的共享接口和可复用实现仍然不足。因此许多 full-stack harness 会重复实现状态、策略钩子和评估轨迹格式。

## 九个技术挑战

论文的技术挑战部分可以读成一张“耦合地图”：每个问题表面上属于某个组件，落到生产系统时都会牵连多个组件。

| 挑战 | 牵连组件 | 核心问题 | 设计启发 |
|---|---|---|---|
| 沙箱与安全 | $E,T,C,S,L$ | 智能体的风险来自行动、工具组合、环境内容和持久状态 | 只做输入过滤覆盖不了工具结果、记忆写入和沙箱逃逸 |
| 评估与基准 | 全部组件 | 分数反映模型、harness、环境三者组合 | 评估报告应披露 harness 配置、环境隔离、成本和异常行为 |
| 协议标准化 | $T,E,L,S$ | MCP 管工具访问，A2A 管智能体间委托，二者边界仍需桥接 | 标准协议还需要身份、授权、状态继承和审计语义 |
| 运行时上下文管理 | $C,S,L,V$ | 长上下文提高容量，也带来注意力稀释、成本和安全滞留 | C 组件要做信息调度；只做截断或堆叠容易产生上下文腐化（context rot） |
| 知识与上下文工程 | $C,S$ | 技能、记忆、检索和摘要决定模型可用知识 | 技能包需要治理和验证，自生成技能可能引入噪声 |
| 工具使用治理 | $T,L,S$ | 工具目录大小、结构定义、权限组合和错误处理影响可靠性 | 工具注册表要做能力裁剪、结构定义校验、版本控制和组合策略 |
| 记忆架构 | $S,C,L$ | 写什么、怎么检索、保留多久、谁能读取都属于治理 | 记忆系统需要类似数据库的持久性、一致性、隔离和审计契约 |
| 规划循环治理 | $E,C,S,L$ | 树搜索、反思、回滚和预算控制都需要 harness 管理 | 规划越复杂，越需要 harness 维护分支状态、预算和终止条件 |
| 多智能体协作 | $E,S,L,T,V$ | 身份、消息模式、共享状态和授权传播产生新故障面 | 多智能体收益需要超过协调成本，尤其要对比优化过的单智能体基线 |

### 安全：攻击面来自组件组合

智能体 harness 的安全问题比普通文本安全更贴近系统安全。恶意内容可以来自用户输入、检索内容、工具输出、跨智能体消息或长期记忆；危害可以通过工具组合放大，例如文件读取、文件写入和 shell 执行组合起来产生高权限行动空间。

论文把攻击持久性和组件深度对应起来：$C$ 层注入多为会话级，$S$ 层记忆污染可以跨会话，$E$ 层沙箱逃逸可能变成系统级问题。这使得 harness 安全需要分层防御：执行环境隔离、工具权限裁剪、上下文来源标记、状态写入验证、生命周期钩子审计、人类审批和回滚机制。

### 评估：单位是轨迹

传统 NLP 评估常比较一个字符串输出；智能体评估要比较一条轨迹。轨迹具有路径依赖：第 $n$ 步是否正确取决于前面所有环境变化。它还具有 harness 耦合：同一个模型换一个工具结构、上下文策略、沙箱镜像或评估接口，结果可能明显不同。

因此，$V$ 组件应记录足够多的信息，让研究者能区分模型失败、环境漂移、任务说明歧义和 harness 失效。对 [[SWE-Bench]] 这样的可执行基准来说，仓库快照、依赖、测试运行器、patch 应用方式和失败日志都属于评估证据的一部分。

### 上下文、记忆与成本：harness 是调度器

论文把上下文管理看成调度问题。短上下文时代，主要问题是保留什么；长上下文时代，主要问题是让模型注意到什么。超长上下文模型扩大了容量，也会引入注意力稀释、token 成本和旧注入内容长期滞留的问题。

记忆层同样是 harness 治理对象。MemGPT 把上下文窗口类比为内存（RAM），把外部存储类比为磁盘（disk）；Reflexion 存储失败后的语言化自我批评；Voyager 存储可复用技能；知识图谱式记忆存储实体和关系。它们的共同问题是：写入是否经过验证、检索是否可信、不同智能体或用户的记忆是否隔离、长期记忆能否审计。

### 工具与协议：注册表就是治理面

工具注册表决定智能体的行动空间。工具越多，覆盖面越广，选择噪声、token 开销和安全风险也会上升。论文提到的实践证据支持“按任务裁剪工具集合”：大工具目录适合后端管理，模型每一步看到的工具应尽量精炼。

[[Model Context Protocol|MCP]] 可以理解为 $T$ 组件的开放接口标准，主要处理智能体到工具的访问；[[A2A Protocol|A2A]] 更接近多 harness 或多智能体的任务委托层，主要处理智能体之间的协作。二者的缺口在授权传播：当 A2A 委托来的任务需要调用本地 MCP 工具时，harness 还需要把外部任务身份转成内部工具权限。

### 规划与多智能体：治理开销需要收益证明

规划越复杂，harness 承担的状态责任越重。线性 ReAct 循环只需要 step limit、工具校验和观察注入；Tree of Thoughts 或 MCTS 需要保存分支、分配 rollout 预算、回滚失败路径、记录反思，并在预算耗尽时做可解释的提交。

多智能体系统进一步引入身份、消息校验和共享状态一致性。角色式协作需要原子文档交接，市场式协作需要智能体注册表和负载状态，仿真式协作需要世界状态冲突处理，层级委托需要权限沿委托链传播。论文提醒：同质多智能体组合经常被协调成本抵消，异质智能体组合才更可能产生稳定收益。[[KV Cache]] 复用、单智能体强基线和工具裁剪应作为多智能体方案的对照组。

## 与 Agent Harness Engineering (2026) 的关系

[[Agent Harness Engineering (2026)]] 提出 ETCLOVG 七层分类：执行环境、工具接口、上下文管理、生命周期/编排、可观测性、验证/评估、治理/安全。本文提出 ETCSLV 六组件框架：执行循环、工具注册表、上下文管理器、状态存储、生命周期钩子、评估接口。

两篇综述的共同点是把智能体可靠性放到模型外部基础设施中理解，并把 [[SWE-Bench]]、Codex 类代码智能体、HAL/AgencyBench 这类评估系统看成 harness 研究的关键证据。差异在于分析粒度：ETCLOVG 更像工程分层图，适合排查生产系统责任边界；ETCSLV 更像运行时治理接口，适合比较系统完整性、讨论形式化语义和构造完整性矩阵。

如果要把两者合并使用，可以把 ETCSLV 当作“运行时最小接口集”，把 ETCLOVG 当作“生产工程扩展视图”。例如，ETCSLV 的 $L$ 覆盖很多治理和安全钩子，ETCLOVG 会把治理/安全单独提升为层；ETCSLV 的 $V$ 覆盖评估接口，ETCLOVG 会把可观测性和验证/评估拆成两个工程面。

## 研究路线

论文的研究路线可以压缩成四组问题。

第一组是跨组件耦合。上下文保留和安全相互牵制：保留越多，任务连续性越强，恶意内容也越容易滞留。评估接口和生命周期钩子都要拦截执行流，可以共享事件层。工具调用和状态写入经常同时发生，需要统一表示“这个工具调用改变了哪些持久状态”。

第二组是可观测和评估。未来 harness 需要结构化轨迹、断点式中断、确定性回放和成功/失败轨迹差分分析。[[Agent Evaluation|智能体评估]] 也需要从“最终成功率”扩展到成本、部分完成度、行为异常和人工可接受性。

第三组是自动化 harness 工程。Meta-Harness 说明 harness 设计空间可以被搜索：外层智能体生成 harness 候选，评估器跑基准，轨迹反馈再进入下一轮搜索。这个方向把 harness 质量从纯人工工程问题推进到可优化对象。

第四组是形式化和互操作。长期方向包括 harness 行为不变量、组件组合验证、跨 harness 基准、MCP/A2A/proprietary 之间的协议桥、长程任务分解、工具组合推断、记忆接口标准化和能耗感知基础设施。

## 边界与阅读提醒

> [!warning] 局限性
> 这篇论文是 preprint，且正文中对系统数量和研究方向数量存在 22/23、12/14 的表述差异。本笔记按完整性矩阵的 23 个系统与后文路线图的 14 个方向理解。论文的闭源系统评级依赖公开文档，适合作为架构对比线索，不能直接等同于内部真实实现。

> [!warning] 使用边界
> 六组件框架适合讨论运行时治理覆盖面；它对组件之间耦合做了抽象。真实系统里 $E$ 和 $S$、$C$ 和 $L$、$V$ 和 $L$ 会紧密相互影响，单独优化某个组件容易把失败转移到组件边界。

## 面试视角

> [!interview] Q: 什么是智能体 harness？
> A: 智能体 harness 是围绕 LLM 智能体的运行时治理基础设施，负责执行循环、工具注册、上下文管理、状态持久化、生命周期策略和评估轨迹。它把模型的潜在能力转化为可执行、可恢复、可审计的系统行为。

> [!interview] Q: 为什么论文把 harness 写成 $\mathcal{H}=(E,T,C,S,L,V)$？
> A: 这六个组件覆盖三类治理面：$E,T$ 管外部行动，$C,S$ 管信息和状态，$L,V$ 管策略与证据。少了 $E$，系统只剩单次调用；少了 $T$，智能体无法作用于世界；少了 $S,L,V$，长程任务的恢复、安全和评估都会变脆。

> [!interview] Q: Harness 和开发框架有什么区别？
> A: 开发框架提供构建智能体的开发原语，例如图、链、检索器或工具调用封装；harness 负责智能体跑起来之后的运行时治理，包括终止、恢复、权限、状态、轨迹和评估。LangGraph 更偏构建框架，Claude Code 或 OpenHands 更接近全栈 harness。

> [!interview] Q: 为什么同一个模型在不同 harness 里表现不同？
> A: Harness 决定模型看到的上下文、可调用的工具、错误格式、重试策略、状态持久化和评价接口。长程任务会把这些差异逐步放大，所以最终分数通常是“模型-harness-环境”组合的结果。

## 速查

> [!example] 六组件速记
> - $E$：循环，任务如何推进和终止
> - $T$：工具，行动空间如何定义和约束
> - $C$：上下文，模型每一步看到什么
> - $S$：状态，什么会跨轮次或跨会话留下来
> - $L$：生命周期，哪些事件被拦截、审计、审批和策略化
> - $V$：评估，轨迹如何变成可比较的证据

> [!example] 判断一个系统是否属于完整 harness
> 先问它是否有明确执行循环 $E$ 和工具注册表 $T$；再看它是否能管理上下文 $C$、持久状态 $S$、策略钩子 $L$ 和标准评估接口 $V$。如果只能帮你搭建智能体，但恢复、权限、状态和评估都要自己补，它更像开发框架。
