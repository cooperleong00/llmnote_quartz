# Agent Systems with Harness Engineering (2026)

这篇综述把智能体系统（agent system）的能力解释为 **基础模型（foundation model）与 harness 的联合产物**。Harness 是围绕模型的执行基础设施，负责工具调用、状态维护、上下文构造、错误恢复、安全控制和多步协作；harness engineering 研究如何同时优化这套基础设施和模型本身，让长程智能体在真实环境中稳定行动。

这篇论文适合作为独立综述笔记阅读，因为它覆盖多个独立贡献：概念基础、harness 设计组件、模型侧适配、评测版图和未来方向。它与 [[Agent Harness Engineering (2026)|Agent Harness Engineering: A Survey]] 和 [[Agent Harness for Large Language Model Agents (2026)|Agent Harness for LLM Agents]] 的关系是互补的：前者用 ETCLOVG 七层分类描绘生产级 harness，后者用 $\mathcal{H}=(E,T,C,S,L,V)$ 定义运行时组件，本篇把 scaffold 侧设计、模型侧适配和 harness capacity 评测放进同一个闭环。

## 一句话定位

Harness engineering 的核心问题是：**怎样让一个以单次文本生成为接口的模型，在需要持续观察、行动、记忆、验证和恢复的环境里表现成可靠的智能体系统**。答案由两部分组成：scaffold 侧构造更好的执行基础设施，模型侧通过 [[Context Engineering|上下文工程]] 和 [[Agentic RL|agentic training]] 学会利用这些基础设施。

> [!intuition] 核心直觉
> 单次模型调用像一次判断；智能体任务像一段运行中的程序。Harness 提供循环、状态、工具、安全边界和外部反馈，让模型的每次判断都落在可执行、可检查、可恢复的运行时里。

## 为什么需要这个视角

论文从一个结构性缺口出发：大语言模型（LLM）原生接口偏向单轮生成，真实任务偏向有状态、多步、可反馈的过程。长程任务里常见的失败包括中间目标丢失、工具参数错误、无法吸收环境反馈、上下文膨胀、失败后缺少恢复路径。论文把这些现象统一解释为 **模型接口与任务运行形态之间的错配**。

在这个视角下，智能体系统可以分成两个基本部分：

| 部分 | 作用 | 典型能力 |
|---|---|---|
| 基础模型 | 推理、语言理解、生成和局部决策 | 读懂任务、形成计划、选择动作、解释反馈 |
| Harness | 把模型放进可执行环境 | 工具调用、上下文组装、状态持久化、权限控制、错误恢复、评测记录 |

这两个部分形成相互放大的关系。更强的模型能执行更复杂的工作流；更好的 harness 能把环境状态、工具结果和失败反馈组织成模型可用的信息。Harness engineering 因此关注系统层优化：设计 harness 时要理解模型的能力边界，训练或适配模型时也要面向 harness 暴露的行动空间和反馈形式。

## Harness Engineering 的三层含义

论文把 harness engineering 的含义分成三个逐步扩展的层次。读这三层时，可以把它们看成从“系统由什么组成”到“怎样构建系统”，再到“怎样联合优化系统”的认知路径。

| 层次 | 问题 | 解释 |
|---|---|---|
| 结构分解 | 智能体系统由什么组成 | 系统由基础模型和支撑 harness 构成；harness 负责模型与环境之间的交互、状态和控制 |
| 框架构建 | 如何搭建可复用智能体框架 | harness 被实现为工作流、工具接口、执行环境、记忆、权限和多步任务管理 |
| 协同增强 | 如何最大化系统级能力 | scaffold 侧优化基础设施，模型侧通过上下文组织与训练适配 harness，两侧共同决定可靠性、可扩展性和可控性 |

这里最重要的是第三层。只做框架封装时，工程重点落在工具和工作流；进入协同增强后，问题会变成：模型需要怎样的上下文才能正确调用工具，训练环境怎样暴露可学习的反馈，记忆和技能怎样以低成本进入推理过程，评测怎样区分模型贡献与 harness 贡献。

## 演化路径：从接口到持久助手

论文把 harness 的演化概括为三层基础设施扩展。

### 1. 动作接口：连接模型与环境

最早的 harness 主要承担动作接口（action interface）：模型输出动作，harness 把动作翻译成工具调用，再把观察结果送回模型。[[ReAct]] 展示了这种“推理-行动-观察”循环；后续系统把文件操作、浏览器、代码执行、API 调用和沙箱环境统一进这个循环。

这一层解决的是“模型如何触碰世界”。它的核心难点在于动作空间设计：通用接口如 bash 灵活度高，安全校验和参数约束较弱；结构化接口如 [[Model Context Protocol|MCP]] 能提供结构定义（schema）、权限边界和可发现性，灵活性会受到协议表达能力限制。

### 2. 工作流基础设施：管理持久工作区

第二层把 harness 扩展成工作区编排器。代码智能体需要反复检查文件、修改代码、运行测试、读取报错、再继续修复；这个循环需要文件系统、shell、版本控制、依赖环境、测试运行器和恢复策略共同支撑。[[SWE-Bench]] 能成为代码智能体的核心基准，正因为它把 issue 修复放进真实仓库和可执行测试里。

在这一层，harness 管理的是“任务如何持续推进”。模型的一次输出只是循环中的一步，工作区状态、测试反馈和中间产物才是长期任务的主线。

### 3. 用户中心持久性：跨会话连续性

第三层把 harness 推向个人助手和长期代理。系统需要记住用户偏好、项目背景、历史决策、例行任务和跨渠道状态。这里的持久性已经超出单个任务，进入用户画像、长期记忆、任务队列、授权边界和多代理协作。

这一层的核心问题是“同一个用户的长期上下文怎样被可靠维护”。这会把记忆治理、隐私、权限、过期策略和跨应用协议变成 harness 的一等设计对象。

## Scaffold 侧设计：四个核心组件

论文把支架侧（scaffold）harness 设计分成四个组件：[[Agent Workflow|智能体工作流]]、[[Agent Memory System|记忆系统]]、[[Skill Library|技能库]] 和 [[Multi-Agent Orchestration|多智能体编排]]。它们共同把模型的局部推理组织成长程行动。

| 组件 | 负责的问题 | 设计重点 |
|---|---|---|
| 智能体工作流 | 感知、规划、行动如何循环 | 环境感知、任务分解、工具调用、失败恢复 |
| 记忆系统 | 哪些状态进入上下文、外部存储或长期记忆 | 短期工作记忆、会话记忆、语义记忆、情节记忆、程序性记忆 |
| 技能库 | 成功经验如何变成可复用能力 | 技能获取、表示、检索、版本管理、退役和安全验证 |
| 多智能体编排 | 复杂任务如何在多个上下文和角色之间分配 | 中央协调、去中心协作、通信压缩、共享工件和验证子代理 |

### 智能体工作流：把单步生成变成执行循环

智能体工作流是 harness 的运行核心。模型本身在一次前向传播后就结束，持续行为来自 harness 对历史、工具和环境反馈的反复组织。一个典型循环包括三步：

1. **环境感知**：从网页、桌面、代码库、API 或沙箱中提取任务相关状态。
2. **任务规划**：把目标分解成可验证的中间步骤，并根据反馈调整计划。
3. **行动执行**：调用工具、修改环境、收集结果，然后进入下一轮。

环境感知的关键取舍是 **信息完整度、token 效率和可靠性**。文本化 DOM 容易解析但冗余，截图有视觉信息但定位可能模糊，多模态抽取更完整也更昂贵。高质量 harness 会把对决策有用的信息放进上下文，把冗长细节写入可查询文件或外部状态。

任务规划的关键取舍是 **校准点密度与成本**。更细的分解能让工具执行成为校验点，降低长链推理的误差累积；更细的分解也会带来更多模型调用、更多上下文切换和更多工具开销。可靠系统会把计划作为持续更新的工件，而非一次性输出。

行动执行的关键取舍是 **行动空间自由度与安全控制**。通用工具能覆盖更多场景，结构化工具能提供参数验证、权限裁剪和审计记录。面向高风险部署时，harness 需要沙箱、权限隔离、工具结果过滤和执行轨迹审计。

### 记忆系统：把状态按生命周期管理

论文强调，记忆的目标是保留对未来决策有价值的信息。短期记忆管理当前会话中的中间状态，长期记忆积累跨会话的知识、经验和程序。

> [!intuition] 记忆的治理原则
> 工具结果通常可以重新获取，优先清理；用户决策、失败原因、任务检查点和项目约束更难重建，需要压缩或持久化。记忆管理的核心是根据信息的可重建性和复用价值决定它的生命周期。

短期记忆包括工作记忆和对话记忆。工作记忆保存当前任务的中间结论、计划和观察；对话记忆保存用户偏好、先前承诺和跨轮次决策。[[Context Compression|上下文压缩]]、摘要、分页检索和结构化检查点都服务于同一个目标：在有限上下文窗口里保留高决策价值信息。

长期记忆可以分成三类：语义记忆保存事实和用户偏好，情节记忆保存过去的交互轨迹和成败经验，程序性记忆保存可复用工作流。程序性记忆继续稳定下来，就会靠近技能库。

### 技能库：把经验沉淀成可调用能力

技能库解决重复探索问题。一个智能体如果每次遇到相似任务都重新阅读文档、试错工具和重建流程，长程任务成本会迅速膨胀。技能把成功行为包装成可检索、可加载、可版本化的行为单元。

技能来源有三类：

| 来源 | 机制 | 风险 |
|---|---|---|
| 示范学习 | 从专家轨迹、工具日志或强模型输出中抽取技能 | 轨迹可能过窄，迁移到新场景时脆弱 |
| 经验学习 | 从智能体自己的环境交互中提炼成功流程 | 需要稳定反馈，错误技能可能被持久化 |
| 外部资源 | 从文档、代码库、API 定义和人工包中构造技能 | 依赖会过期，包可能存在安全或供应链风险 |

技能管理的关键是渐进披露（progressive disclosure）。运行时先给模型技能名称、描述或索引，只有当任务需要时才加载完整说明、脚本、测试或资源。这样技能库可以扩展到远超上下文窗口的规模。

技能维护是容易被低估的部分。工具 API 变化、依赖迁移、重复技能、过时经验和恶意技能都会降低系统可靠性。把技能当作软件包后，harness 需要版本控制、兼容性测试、冲突检测、退役机制和激活前安全验证。

### 多智能体编排：用多个上下文换取专业化和并行性

多智能体编排通过多个智能体分担任务。它带来三个主要收益：每个智能体有独立上下文窗口，子任务可以并行运行，不同智能体可以携带不同工具和角色。

论文区分两类协调架构。中央式架构由一个控制器分解任务、分配子任务和汇总结果；去中心架构让智能体通过共享状态、对话或工件协作。生产系统中很实用的一种模式是验证子代理：主代理完成任务，验证代理用尽量少的上下文黑盒检查结果，例如运行测试、审阅输出或复现关键步骤。

通信机制决定多智能体是否形成真正协作。只共享最终答案会丢失隐含决策；共享完整轨迹会制造巨大通信成本。较好的折中是共享关键决策摘要、工件、测试结果和待解决冲突。对于写入型任务，还需要更强的合并协议，因为多个智能体同时修改同一对象会产生不一致。

## 模型侧适配：让模型学会利用 Harness

Harness engineering 的另一半是模型侧适配。论文把它分为 [[Context Engineering|上下文工程]] 和智能体训练（agentic training）。前者在推理时组织模型输入，后者通过 [[SFT]]、[[PPO]]、[[DPO]]、[[GRPO]] 等训练方法把智能体行为内化到参数里。

### 上下文工程：决定模型每一步看到什么

上下文工程在智能体 harness 中有两个阶段：上下文设计和上下文管理。

上下文设计负责行动前输入。提示词工程提供角色、规则、示例和输出格式；[[RAG|检索增强生成]] 提供外部知识；智能体式检索（agentic retrieval）让检索成为行动循环的一部分，模型可以边推理边查询。与普通问答里的检索相比，智能体式检索更关心检索时机、查询重写、工具状态和后续行动。

上下文管理负责长程运行中的信息压缩、更新和重组。长任务会积累历史、工具结果、计划、失败原因和中间产物。Harness 需要决定哪些内容留在活跃窗口，哪些内容压缩成摘要，哪些内容写入外部存储，哪些内容可以丢弃。这里的难点在于过度压缩会丢失约束，过少压缩会让上下文腐化和成本失控。

### Agentic training：把多步交互能力训练进模型

Agentic training 面向交互式环境训练模型，目标是让模型更擅长工具调用、多步规划、环境反馈利用和长期任务执行。它需要四个支柱：

| 支柱 | 问题 | 例子 |
|---|---|---|
| 环境构造 | 训练反馈来自哪里 | 规则验证环境、模拟环境、真实网页/代码/机器人环境 |
| 优化算法 | 参数怎样更新 | [[SFT]] 学习轨迹，[[PPO]] 和 [[GRPO]] 用环境奖励优化策略，[[DPO]] 等偏好方法降低在线探索成本 |
| 监督信号 | 奖励如何定义 | 任务完成奖励、测试通过、工具调用正确性、过程奖励模型 |
| 训练基础设施 | 如何规模化 rollout 和更新 | 分布式推理、环境调度、异步生成、参数同步、多智能体 rollout |

环境保真度决定训练迁移。规则环境有清晰奖励，适合数学、代码和可执行验证；模拟环境成本较低，难点是仿真偏差；真实环境反馈最可信，安全、成本和可复现性压力也最大。

奖励粒度决定学习信号密度。结果级信号适合最终可验证任务，例如测试是否通过；过程级信号能指出哪一步规划、工具选择或观察解释出了问题，更适合长程任务里的信用分配。

## Harness Capacity：评测单位从答案转向运行轨迹

论文提出 harness capacity，用来指智能体系统在工具使用、部分可观测、长执行轨迹和变化环境中维持有效行动的能力。这个概念提醒我们：评测智能体时，最终答案只是结果；真正需要观察的是系统如何维护目标、选择工具、更新状态、处理失败并控制成本。

论文梳理了五类评测场景：

| 场景 | 评测重点 | 代表基准 |
|---|---|---|
| Deep research | 多步搜索、证据积累、引用质量、报告组织 | BrowseComp, DeepResearch Bench, ResearchRubrics |
| 软件工程 | 仓库理解、issue 修复、测试反馈、跨文件一致性 | [[SWE-Bench]], SWE-Bench Pro, BeyondSWE |
| 工具使用和函数调用 | 工具选择、参数填写、多步工具编排、状态一致性 | API-Bank, BFCL, ToolSandbox, $\tau$-bench |
| 电脑使用和 GUI grounding | 多模态感知、界面元素定位、浏览器/桌面/移动端控制 | WebArena, OSWorld, OSWorld-MCP |
| ML 工程和科学研究 | 实验循环、复现、开放式科学工作流 | MLAgentBench, MLE-bench, PaperBench, ReplicatorBench |

评测的趋势是从单一最终分数走向多信号画像。一个高质量 harness 基准应记录执行轨迹、状态更新、工具调用、失败恢复、中间工件、成本、权限事件和安全检查。这样才能分析成绩来自模型、harness、工具、环境还是评分器。

> [!warning] 评测边界
> 如果只看最终成功率，harness 的改动很容易被误读成模型能力提升。Agent 系统评测应报告模型-harness 组合、运行环境、工具集合、上下文策略、重试预算和验证机制。

## 未来方向：从能力构建走向运行时治理

论文的未来方向可以概括为 [[Runtime Governance|运行时治理]]：当智能体能持续行动、写入状态、委托子任务和调用高权限工具后，harness 的核心责任会转向资源、状态和行动约束。

| 方向 | 核心问题 | 设计启发 |
|---|---|---|
| 效率 | 计算、上下文和工具调用如何按风险分配 | 动态模型路由、轨迹压缩、缓存、例行任务走低成本路径 |
| 安全 | 工具、记忆和委托如何被权限和审计约束 | 工具输出过滤、MCP 元数据防污染、路径依赖策略、审批和回滚 |
| 持续学习 | 经验怎样长期影响未来行为 | 记忆过期、冲突合并、技能版本化、来源与新鲜度元数据 |
| 状态与环境建模 | 智能体如何维护行动相关的世界状态 | 显式信念状态（belief state）、状态转移模型、沙箱日志、GUI/网页状态图 |
| 具身 harness | 物理行动如何验证和恢复 | 感知可靠性检查、动作前验证、失败后安全退回、人类接管 |
| 评测 | 如何评估完整运行过程 | 轨迹级指标、状态质量、安全质量、成本质量、模型-harness 归因 |

安全方向尤其重要。文本输出风险主要发生在生成端；工具、记忆和行动权限加入后，风险会沿着观察-行动循环传播。工具结果可能携带提示注入，工具元数据可能被污染，记忆可能长期保存不可信内容，子代理可能带着不完整上下文执行高风险动作。Harness 需要让工具输出、记忆条目、检索文档和计划动作携带来源、信任度和新鲜度，并在下游使用前重新校验。

## 设计启发：如何检查一个 Agent 系统

如果要用这篇论文评估或设计一个智能体系统，可以沿着以下问题检查：

1. **行动循环是否清楚**：模型怎样观察环境、生成计划、执行动作、接收反馈和终止？
2. **状态生命周期是否清楚**：哪些信息在上下文里，哪些写入文件、记忆或数据库，哪些可以清理？
3. **工具边界是否清楚**：工具如何发现、校验参数、裁剪权限、记录结果和处理失败？
4. **技能和记忆是否被治理**：经验怎样沉淀，怎样过期，怎样防止冲突和污染？
5. **多代理是否有收益证明**：拆分是否保护上下文、带来并行或增强专业化，通信成本是否可控？
6. **模型是否适配 harness**：训练数据和奖励是否覆盖真实工具、环境反馈、多步恢复和失败归因？
7. **评测是否记录过程**：日志是否足以重放轨迹、归因失败、计算成本并检查安全事件？

## 边界与局限

> [!warning] 理解边界
> - Harness engineering 很容易扩大成“所有系统工程”的总称。实用边界应围绕模型与环境之间的运行时接口：上下文、工具、状态、执行、权限、反馈和评测。
> - 更复杂的 harness 会带来更强能力，也会带来更多调试面、权限面和维护成本。设计时需要证明每个组件对任务可靠性、成本或安全的贡献。
> - 多智能体结构会消耗额外 token、时间和协调成本。只有当上下文隔离、并行执行或角色专业化带来明确收益时，它才值得引入。
> - 记忆和技能具有持久影响。低质量记忆、过期技能、污染工具描述和不完整审计会让错误跨会话传播。
> - 评测结果应绑定具体模型、harness、工具集合和环境版本。缺少这些上下文时，排行榜分数很难转化为工程决策。

## 面试视角

> [!interview] Q: Harness engineering 和提示词工程、上下文工程有什么关系？
> A: 提示词工程主要组织单次调用的指令和示例；[[Context Engineering|上下文工程]] 管理多步运行中模型可见的信息状态；harness engineering 覆盖更大的运行时系统，包括工具、执行环境、记忆、状态、权限、编排、评测和模型侧适配。上下文工程是 harness engineering 的模型侧组成部分。

> [!interview] Q: 为什么强模型仍然需要 harness？
> A: 强模型能提高局部推理质量，但长程任务还需要环境感知、工具执行、状态持久化、失败恢复和权限控制。Harness 把这些能力组织成可持续运行的闭环，让模型的局部决策连接到真实任务进展。

> [!interview] Q: 如何判断一个智能体基准是否真正评估了 harness capacity？
> A: 看它是否要求多步环境交互，是否记录工具调用和状态变化，是否检查失败恢复、成本和安全事件，是否能区分模型、harness、工具和环境带来的影响。只有最终答案的基准，对 harness 的诊断价值有限。
