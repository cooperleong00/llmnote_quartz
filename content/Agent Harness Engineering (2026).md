# Agent Harness Engineering (2026)

Agent Harness Engineering: A Survey 把 LLM 智能体（LLM agent）的可靠性问题放到模型外部的执行基础设施中理解。它的核心判断是：在长程、多步任务里，结果由模型和 [[Agent Harness|agent harness]] 共同决定；当模型能力接近时，harness 的设计质量会显著影响任务成功率、成本、安全性和可诊断性。

## 一句话定位

这篇综述提出 **ETCLOVG** 七层分类：执行环境（Execution Environment）、工具接口（Tool Interface）、上下文管理（Context Management）、生命周期与编排（Lifecycle/Orchestration）、可观测性（Observability）、验证与评估（Verification/Evaluation）、治理（Governance）。它把智能体系统从“模型调用 + 工具列表”的视角推进到“可执行、可观测、可回滚、可治理的控制系统”视角。

这篇论文适合作为综述型论文笔记阅读，因为它的贡献集中在分类框架、生态映射和跨层综合，涵盖多个独立工程面。它与 [[Agentic RL]] 的关系在于：Agentic RL 关注如何训练多步决策能力，这篇综述关注这些能力在真实系统中如何被执行环境、工具协议、上下文、状态机、评估和治理约束成可靠行为。

## 为什么需要 Harness Engineering

早期智能体系统常以 ReAct 风格的观察-思考-行动循环（observe-think-act loop）为中心：模型读入状态，产生行动，工具返回观察，模型继续下一步。这个循环足以解释基本交互，却难以解释长程系统中的四类问题：执行环境会漂移，工具接口会误导模型，上下文会膨胀或丢失关键状态，评估分数会混入沙箱（sandbox）、评分器（grader）和编排（orchestration）噪声。

论文把 2022-2026 的工程演化概括为三个阶段：

| 阶段 | 主要工程对象 | 典型问题 |
|---|---|---|
| 提示词工程（Prompt Engineering） | 单次模型调用的输入文本 | 怎样写指令、示例和输出格式 |
| [[Context Engineering|上下文工程]]（Context Engineering） | 每一步模型可见的信息状态 | 什么信息该进入窗口，怎样压缩、检索和放置 |
| Harness 工程（Harness Engineering） | 围绕模型的执行、工具、状态、反馈和约束系统 | 智能体如何在长时间、多工具、多权限环境中可靠行动 |

> [!intuition] 核心直觉
> 长程智能体的失败经常发生在模型和世界的接口处。模型可能有能力推理出下一步，但 harness 决定它看到什么状态、能调用哪些工具、工具结果如何回流、失败如何恢复、哪类行动需要审批、运行结果如何评估。Harness 工程研究的就是这些接口和控制回路。

## Binding-Constraint Thesis

论文的核心论点可以称为 **约束瓶颈论点（binding-constraint thesis）**：在长程任务和同等级前沿模型（frontier models）的比较中，智能体表现的瓶颈经常来自执行 harness。论文列举了三个来自 2026 年的“只改 harness”证据：只修改编辑工具格式（edit-tool format）和周边 harness，可在代码基准上带来最高 10 倍提升；固定模型的 Codex 智能体通过提示词重构、中间件上下文注入和自验证钩子，在 Terminal-Bench 2.0 上从 52.8% 提升到 66.5%；Meta-Harness 通过自动 harness 优化在 Terminal-Bench-2 上达到 76.4%。

这个论点对评估方式有直接影响。一个智能体基准的分数应被理解为 **模型-harness 组合（model-harness pair）** 的表现：模型权重、工具结构定义（tool schema）、沙箱镜像、上下文策略、权限规则、评分器、重试循环都会改变最终轨迹。[[SWE-Bench]] 这类可执行基准尤其能体现这一点，因为补丁是否通过测试既取决于模型生成代码的能力，也取决于仓库快照、依赖安装、测试运行器、shell 访问权限和重置语义。

## ETCLOVG 七层分类

ETCLOVG 的前四层构成 agent harness 的结构核心，后三层构成控制平面。读这个分类框架时，可以把它看成一张“故障定位地图”：当智能体失败时，问题可能落在模型推理，也可能落在任意一个 harness 层。

| 层 | 设计问题 | 关键机制 | 常见失效 |
|---|---|---|---|
| **E - 执行环境（Execution Environment）** | 智能体的行动在哪里执行 | 沙箱、容器、microVM、浏览器/桌面环境、操作系统级权限边界 | 沙箱逃逸、环境不可复现、依赖漂移、重置成本过高 |
| **T - 工具接口（Tool Interface）** | 智能体如何发现和调用外部能力 | 函数调用（function calling）、OpenAPI、[[Model Context Protocol|MCP]]、A2A、工具注册表、工具检索 | 工具太多导致选择错误，结构定义模糊，工具描述被污染 |
| **C - 上下文管理（Context Management）** | 每一步模型应该看到什么 | [[Context Engineering|上下文工程]]、渐进披露（progressive disclosure）、分层记忆、[[Context Compression|上下文压缩]]、面向 KV-cache 的顺序安排 | 上下文腐化、上下文漂移、摘要丢失约束、检索错位 |
| **L - 生命周期与编排（Lifecycle/Orchestration）** | 任务如何跨回合、失败和交接持续推进 | 单智能体循环、多智能体编排、任务运行器、检查点/恢复、从 issue 到 PR 的流水线 | 过早宣布完成、循环、状态不一致、交接信息丢失 |
| **O - 可观测性（Observability）** | 如何知道智能体做了什么和为什么 | 轨迹树、OpenTelemetry span、成本追踪、会话回放、认知可观测性 | 只能看到最终失败，看不到失败来源；成本和延迟不可归因 |
| **V - 验证与评估（Verification/Evaluation）** | 如何把执行轨迹变成工程证据 | 基准任务落地检查、就绪性验证、轨迹原生评估、失败归因、回归测试集 | 排行榜分数混入环境噪声，评分器不稳定，回归测试覆盖不足 |
| **G - 治理与安全（Governance/Security）** | 智能体在什么权限和责任边界内行动 | 权限模型、身份、生命周期钩子、策略 DSL、审计日志、人类审批 | 提示注入、凭证泄露、越权工具调用、审计记录不足 |

论文的一个重要分类选择是把可观测性和治理提升为独立层。可观测性有独立的轨迹、成本、延迟、异常检测和回放工具链；治理有独立的权限、身份、策略、加固、审计和人类介入机制。把它们放在生命周期下面会掩盖生产系统中真实的团队边界和工程责任。

## 每一层真正管什么

### 执行层：给智能体一个可控行动区域

执行层管的是智能体行动的物理承载环境。沙箱在智能体时代同时承担三件事：安全边界、可复现的重置机制，以及让智能体在授权区域内自由行动的活性机制（liveness）。第三点尤其关键：如果每个文件写入、依赖安装、网络调用都要人类审批，长程智能体会卡在权限对话框里；如果用户频繁无脑批准，审批本身会失去安全意义。

这解释了为什么智能体沙箱的选择需要围绕威胁模型（threat model）和任务环境保真度（workload fidelity）做取舍。代码智能体可能使用 Docker、microVM 或操作系统级权限沙箱；浏览器智能体需要真实网页状态；电脑操作智能体需要桌面环境和视觉观察；大规模训练/评估需要快速重置和并行 rollout。

### 工具层：让行动空间可发现、可约束、可评估

工具层管的是外部能力如何暴露给智能体。MCP 代表“智能体到能力”的协议化方向，A2A 代表“智能体到智能体”的协作边界，函数调用和 OpenAPI 仍然是“模型到函数”的基础形式。论文强调，工具能力由三件事共同决定：模型是否学过工具使用，工具结构定义是否清晰，运行时选择策略是否能在当前任务里给出合适工具集合。

对系统设计者来说，工具层的核心问题是行动空间控制（action space control）。工具越多，覆盖面越广，token 开销、选择错误和提示注入攻击面也会变大。可靠 harness 需要动态工具检索、工具候选裁剪、结构定义版本管理，以及能把工具调用错误归因到规划器、协议或具体工具实现的轨迹记录。

### 上下文层：把任务状态投影给模型

上下文层处理模型每一步能看到的信息。论文把 [[Context Engineering|上下文工程]] 放进 harness 工程的内部，因为上下文管理已经从提示词写作发展成多层记忆结构：活跃上下文窗口、会话级持久状态、长期记忆存储。[[Context Compression|上下文压缩]]、渐进披露、按需检索（just-in-time retrieval）和子智能体隔离都是控制这个投影的技术。

这里的深层问题是状态估计（state estimation）。智能体的真实任务状态分散在仓库、文件系统、浏览器、工具结果、审计日志和人类反馈中；模型只能看到 harness 注入的一个压缩视图。每次摘要、检索、清除工具结果都可能改变这个视图。长程失败经常来自智能体的内部状态逐步偏离真实任务状态。

### 生命周期层：把多步行动组织成可恢复流程

生命周期与编排层管的是执行流程和运行状态。单智能体循环适合交互式写代码、调试和解题；多智能体编排通过规划器、执行器、评估器、批评器等角色分工支持并行探索和分阶段验证；完整生命周期流水线把智能体放入 issue、分支、测试、评审、PR 这类外部工作流。

这一层和上下文层的差别在于：上下文层管模型可见的信息，生命周期层管 harness 自己维护的运行状态，例如待处理子任务、检查点、重试元数据、共享产物、执行状态。长程智能体要可靠运行，需要把计划、进度、失败和交接状态写入持久产物；让模型在每次调用中重新推断这些状态，会增加成本和漂移风险。

### 可观测性层：把执行轨迹变成可诊断对象

可观测性层记录智能体运行过程中的模型调用、工具调用、检索步骤、上下文组装、延迟、token 用量、成本、错误、重试和环境变化。普通 LLM 应用可能只需要输入输出日志；agent harness 需要轨迹树（trace tree），因为失败发生在整条行动轨迹中。

论文强调可观测性与评估需要闭环。生产轨迹能生成回归用例，评估失败能变成监控信号。没有这条闭环时，团队能看到智能体做过什么，却难以系统判断这些行为是否正确，也难以把失败反馈到工具结构定义、上下文策略或编排循环。

### 验证层：评估模型-harness 组合

验证与评估层把一次智能体运行看成“任务到反馈”的生命周期。它从任务落地检查开始，确认沙箱、工具、上下文、权限、预算、评分器是否就绪；执行时捕获轨迹；执行后同时评估结果、过程轨迹和评分器；最后把诊断结果放入回归测试集。

这比最终成功率更适合智能体工程。结果级评估告诉我们任务是否完成，轨迹级评估告诉我们过程是否高效、合规、可恢复，评分器级评估告诉我们评分器是否可信。三层证据结合起来，才能判断应该改模型、工具接口、上下文管理器、执行环境、编排循环、基准规范还是评分器。

### 治理层：把能力放进责任边界

治理与安全层管权限、身份、策略、审计和人类审批。智能体能写文件、发邮件、调用企业 API、提交代码，意味着 harness 必须回答：谁授权了这次行动，智能体以什么身份行动，哪个工具调用被允许，凭证如何隔离，哪个策略版本做出了决策，失败后如何审计。

论文把治理拆成权限模型、生命周期钩子、组件加固、声明式规则和审计基础设施。这里的设计挑战在于组合：输入护栏、输出护栏、信息流控制、策略 DSL、人类审批、审计日志各自解决局部风险，组合后的流水线还要控制延迟、误报、策略冲突和用户疲劳。

## 三个跨层效应

### 1. 成本-质量-速度三难

更强的沙箱、更完整的轨迹、更严格的治理、更深的评估通常会增加延迟和成本。生产 harness 需要决定哪些检查同步执行，哪些进入异步分析，哪些只在回归测试集中运行。对于用户交互型智能体，过重的验证会拖慢反馈；对于高风险自动化，轻量检查会留下不可接受的安全和合规缺口。

这条取舍也影响基准解读。一个智能体的高分可能来自更长 rollout、更强模型、更高 token 预算或更多重试，而部署系统关心的是成功率、成本和延迟之间的边界。Harness 评估应记录 token、延迟、工具调用次数、重试次数、沙箱成本和人类审批成本。

### 2. 能力-控制取舍

Harness 暴露更多工具、记忆、网络和执行权限时，智能体能覆盖更多任务，同时控制问题也更复杂。大工具集会提高选择错误概率；持久记忆会带来过期、隐私和来源追踪问题；宽松沙箱会扩大误操作的影响范围；多智能体委托会引入身份和责任追踪问题。

可靠设计需要把能力扩展和控制机制成对加入。例如引入 MCP server 时，同时记录工具定义版本、权限范围和轨迹 id；引入长期记忆时，同时记录来源、时间戳、置信度和删除策略；引入子智能体时，同时定义交接产物、预算、允许工具和返回条件。

### 3. Harness 耦合问题

Harness 的各层会互相耦合，使局部优化变得脆弱。工具描述会占用上下文预算并改变规划器行为；执行环境会改变评估分数；可观测性轨迹只有包含身份和权限状态时，才能成为治理证据；评估指标会奖励某些恢复循环，同时惩罚另一些成本更高但更安全的策略。

因此 harness 变更应按系统变更测试。修改提示词、工具结构定义、记忆策略、沙箱镜像、验证器、权限规则或重试循环，都可能改变同一个模型的测量行为。这个问题也解释了为什么智能体排行榜应说明周边控制器配置，报告模型名称时还要给出 harness 条件。

## 设计启发：如何用 ETCLOVG 设计一个代码智能体 Harness

如果要设计一个面向软件工程的代码智能体 harness，可以沿着 ETCLOVG 逐层提问：

1. **执行**：代码在哪里运行？本地操作系统级权限沙箱、Docker、microVM、云端沙箱还是混合 BYOC？能否快速重置到任务初始状态？
2. **工具**：智能体能调用哪些工具？shell、编辑器、搜索、测试运行器、浏览器、MCP 服务器如何描述、版本化和裁剪？
3. **上下文**：仓库地图、issue、已有修改、测试输出、用户偏好和历史尝试如何进入窗口？什么时候压缩，什么时候检索，什么时候交给子智能体隔离探索？
4. **生命周期**：任务如何从 issue 进入计划、实现、测试、评审、PR？失败后从哪里恢复？何时停止？如何避免过早宣布完成？
5. **可观测性**：每次模型调用、工具调用、文件差异、测试失败、成本和重试是否形成可回放轨迹？
6. **验证**：除了最终测试通过率，是否评估轨迹质量、工具误用、权限违规、成本-延迟边界和评分器稳定性？
7. **治理**：文件、网络、凭证、依赖安装、git 操作和外部 API 调用如何授权？哪些行动需要人类审批？审计日志是否能回答责任归属？

这个流程的价值在于把“智能体靠不靠谱”拆成可定位的工程问题。比如代码智能体在 [[SWE-Bench]] 上失败，可能是模型不会修 bug，也可能是依赖环境没装好、测试命令不一致、仓库状态没重置、上下文里缺关键文件、工具结构定义诱导了错误搜索、重试循环覆盖了原始错误、评分器本身不稳定。

## 边界与局限

> [!warning] 读这篇综述时要保留的边界
> - **语料偏差**：项目映射偏向英文资料、GitHub 可见项目、开源产物，以及公开资料更丰富的代码智能体生态。
> - **公开证据限制**：层级归类依据 README、论文、文档和发布说明；商业生产系统的内部机制通常不可见。
> - **分类框架性质**：ETCLOVG 是描述性框架，能帮助分类和定位问题；具体设计决策仍需结合威胁模型、任务类型、延迟预算和组织约束。
> - **harness thesis 的适用范围**：当模型能力很弱、任务很短或工具需求很少时，模型本身仍可能主导失败。约束瓶颈论点最有解释力的场景是长程、多步、可执行、可评估的智能体工作流。
> - **计数口径变化**：论文不同段落使用 148+、170+ 等项目语料表述，说明快照时间和纳入标准可能在版本迭代中变化。引用生态规模时应保留近似口径。

## 与知识库的连接

这篇论文笔记可以作为 [[Agentic RL]] 的系统侧补充：Agentic RL 提供训练多步智能体的学习框架，harness 工程提供执行这些行为的运行框架。它也延伸了 [[SWE-Bench]] 这类可执行基准的意义：基准既是评估模型能力的工具，也是暴露执行、工具、上下文、验证耦合问题的测量仪器。

在上下文方向，它与 [[Context Compression|上下文压缩]] 的连接最直接：压缩是 C 层的关键技术，但长程可靠性还需要 O/V/G 层提供漂移检测、轨迹诊断和策略执行。未来可以为 [[Context Engineering|上下文工程]]、[[Model Context Protocol]]、[[Trace-Native Evaluation|轨迹原生评估]]、[[Agent Observability|智能体可观测性]] 和 [[Agent Governance|智能体治理]] 建独立笔记，把这篇综述中的分类框架吸收成更细的概念或方法笔记。

## 速查

> [!example] ETCLOVG 记忆法
> - **E**：行动必须在某个环境中执行
> - **T**：能力必须通过某种工具接口暴露
> - **C**：状态必须被投影进模型上下文
> - **L**：任务必须跨步骤持续推进
> - **O**：行为必须变得可观察
> - **V**：行为必须接受验证与评估
> - **G**：行为必须留在授权边界内

> [!interview] 面试视角
> **Q: 为什么这篇综述把可观测性和治理单独列为层？**
> A: 因为它们在生产智能体系统中有独立工具链、团队责任和设计问题。可观测性负责轨迹、成本、延迟、回放、失败诊断；治理负责权限、身份、策略、审计、人类审批。把它们作为独立层，能更准确地定位长程智能体的失败来源。

> [!interview] 面试视角
> **Q: Harness 工程对智能体基准有什么影响？**
> A: 基准分数应解释为模型-harness 组合的结果。改变工具结构定义、沙箱、上下文策略、重试循环、权限规则或评分器，都可能改变同一个模型的表现。因此严谨评估要记录 harness 配置，并把轨迹、结果、过程和评分器可靠性一起纳入分析。
